# Unit 109 — §2.23.2.3 PR reviews, L1467–1471, p.83

Automatic PR monitoring by a prompted Claude (mostly Opus 4.8): common errors, obvious vulnerabilities, and mismatches between a change's stated purpose and actual effect. "Primarily relevant to infrastructure code, as research code is less consistently merged into this primary codebase." Security-invariant tests run automatically where appropriate.

Differed: the PR control covers infrastructure, *not research code* — so for pathways 1–2 (safety research sabotage), PR review mostly doesn't apply. Research code is where sabotage of safety research would live.

Wandering: "mismatches between the stated purpose of a change and its actual effects" — the monitor checks whether the commit message tells the truth about the diff. That's the estate's "report, don't reassure" applied as a security control: a description that doesn't match the artifact is a flag. Nice correspondence.

For the project: invariant tests (e.g. two nodes can't talk) are *executable* controls — machine-checked properties, the strongest kind of barrier. A taxonomy of controls in this report is forming: executable invariants > blocking classifiers > automated monitors > human review > informal skepticism, roughly ordered by mechanisation.
