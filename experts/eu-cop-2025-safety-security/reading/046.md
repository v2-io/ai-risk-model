# Unit 46 · L382–386 · p.18: Measure 6.2, Appropriate security mitigations

**What it held.**
- "Signatories will implement appropriate security mitigations to meet the Security Goal, including the security mitigations pursuant to Appendix 4. If Signatories deviate from any of the security mitigations listed in **Appendices 4.1 to 4.5, points (a)**, e.g. due to the Signatory's organisational context and digital infrastructure, they will implement **alternative security mitigations that achieve the respective mitigation objectives**."
- "The implementation of the required security mitigations **may be staged appropriately in line with the increase in model capabilities** along the entire model lifecycle."

**What differed.** Predicted Appendix 4 and a deviation clause. New: the **structure** of Appendix 4 shows through: sections 4.1–4.5, each with a point (a) (the listed mitigations) and, implicitly, a statement of "mitigation objectives". So Appendix 4 is objective-based: each section states an objective, then lists mitigations; deviating from a listed mitigation is allowed if the objective is met another way. Also new: **staging** security by capability growth.

**Wandering.**
- **Objectives over measures** is the classic security-standards move (cf. ISO 27001 controls vs objectives). It gives flexibility while keeping an auditable target. It also matches recital (f)'s "alternative means" principle, here in a stronger form: deviation is allowed only with alternatives that "achieve the respective mitigation objectives" — the burden is on the signatory to show equivalence.
- **"Points (a)"** only: so the mitigations in other points (b, c…) of each Appendix 4 section are perhaps not deviable, or are of a different kind (e.g. (b) might be stricter requirements at higher tiers). I'll find out in Appendix 4. A fork should not assume all of Appendix 4 is deviable.
- **Staging with capability increase** means early in training, when the model is weak, security can be lighter; as capabilities rise, security must catch up. Danger: capability can jump between checkpoints faster than security can be upgraded (weights at a stronger checkpoint sit on a less secure system). The Code says "staged appropriately", and the trigger points of M1.2 would ideally drive both evaluation and security upgrades. Whether security upgrades are tied to tiers explicitly: M1.1(2)(b) required the Framework to describe the "safety and security mitigations… once each systemic risk tier is reached". So yes: the Framework's tier-to-mitigation mapping covers security too. Coherent.
- "Organisational context and digital infrastructure" as reasons to deviate: e.g. a cloud-native firm can't implement a specific on-prem control. Sensible flexibility.

**Questions to keep.**
- "Are the Appendix 4 security measures mandatory?" M6.2: they're required ("including the security mitigations pursuant to Appendix 4"), but signatories may deviate from those in "Appendices 4.1 to 4.5, points (a)" with "alternative security mitigations that achieve the respective mitigation objectives".
- "Can security be phased in?" Yes, "staged appropriately in line with the increase in model capabilities".

**Prediction for unit 47.** Commitment 7, Safety and Security Model Reports: Signatories commit to reporting to the AI Office about their implementation of the Code, especially the assessment and mitigation per model, through a "Safety and Security Model Report" ("Model Report") before placing a model on the market; Measures 7.1 (model description and behaviour), 7.2 (reasons for proceeding), 7.3 (documentation of systemic risk identification, analysis, and mitigation), 7.4 (external reports), 7.5 (material changes to the risk landscape), 7.6 (Model Report updates), 7.7 (notifications).
