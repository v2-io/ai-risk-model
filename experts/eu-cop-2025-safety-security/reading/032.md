# Unit 32 · L266–278 · p.13: M3.5 example methods (4)–(11); free access for independent external evaluators begins

**What it held.** Example post-market monitoring methods, continued:
- "(4) providing bug bounties;"
- "(5) establishing community-driven model evaluations and public leaderboards;"
- "(6) conducting frequent dialogues with affected stakeholders;"
- "(7) monitoring software repositories, **known malware**, public forums, and/or social media for patterns of use;"
- "(8) supporting the scientific study of the model's capabilities, propensities, affordances, and/or effects in collaboration with academia, civil society, regulators, and/or independent researchers;"
- "(9) implementing **privacy-preserving logging and metadata analysis** techniques of the model's inputs and outputs using, e.g. **watermarks, metadata, and/or other at least state-of-the-art provenance techniques**;"
- "(10) collecting relevant information about **breaches of the model's use restrictions** and subsequent incidents arising from such breaches; and/or"
- "(11) monitoring aspects of models that are relevant for assessing and mitigating systemic risk and are **not transparent to third parties, e.g. hidden chains-of-thought for models for which the parameters are not publicly available for download**."
- Then: "To facilitate post-market monitoring, Signatories **will** provide an **adequate number of independent external evaluators** with **adequate free access** to:" (the list follows in the next unit).
- Conversion note: "(10)collecting" and "(11)monitoring" lack a space in the canonical text.

**What differed.** I predicted bug bounties, research collaborations, social-media monitoring, open-weight monitoring and provenance. Most there. What I didn't predict:
- **(11) hidden chains-of-thought.** A provider of a closed-weight model with hidden reasoning is the only party who can see that reasoning, so it's asked (as an example method) to monitor it. That's chain-of-thought monitoring as a systemic-risk method, in a regulatory text.
- **(7) "known malware"**: watching for the model's outputs or use in malware. Cyber-specific.
- **No open-weight-specific method**, beyond "software repositories" in (7), which would cover watching fine-tunes on hosting sites. The open-weight case is mostly addressed by (11)'s contrast ("models for which the parameters are not publicly available for download").
- A **firm** obligation after the "such as" list: "will provide… free access" to independent external evaluators. Not an example; a duty.

**Wandering.**

- **Chain-of-thought monitoring and the open/closed asymmetry.** (11) limits itself to closed-weight models: "for which the parameters are not publicly available for download". For open-weight models, the reasoning is visible to anyone running the model, so third parties can monitor it; for closed-weight models with hidden CoT, only the provider can. The Code assigns monitoring to whoever can see. That's a principled allocation: responsibility follows visibility. It also implies something about the Code's view of CoT: that it's informative about risk ("relevant for assessing and mitigating systemic risk"). A fork asked "does the Code require CoT monitoring?" should say: it's an example method under M3.5 for closed-weight models with hidden CoT, not a requirement.
- **Privacy-preserving logging, watermarks, provenance.** This is (j)'s pre-incident tracking, with the privacy tension resolved in the wording ("privacy-preserving"). Watermarks and provenance serve attribution: if harmful content appears in the world, can it be traced to the model? "At least state-of-the-art provenance techniques": the state-of-the-art rule even in examples.
- **Use restrictions** (10): the model has "use restrictions" (acceptable use policies, licence terms), and their breaches are information. That's misuse monitoring. It assumes the provider can detect breaches, which works for API access and fails for open weights.
- **Leaderboards and community evaluations** (5): the public as evaluator. It also creates external pressure: a public leaderboard showing a dangerous capability is visible to the AI Office too.
- **Independent external evaluators post-market, with *free* access.** "Adequate number", "adequate free access". The cost of access isn't to fall on evaluators, which matters for academic and civil-society researchers. And it's framed as *facilitating post-market monitoring*: external researchers are part of the monitoring apparatus, not only pre-release testers. I expect the next unit to list what they get access to (the model, its capabilities, maybe model versions without safeguards, maybe CoT?). Watch also for who chooses the evaluators and whether "independent" is defined.
- **The structure of M3.5 so far:** a firm purpose; three firm requirements (four objects; take examples into account; monitor own systems); eleven example methods none of which is mandatory individually; then a firm duty of external-evaluator access. The example list is a menu with an expectation ("take into account the exemplary methods"): a signatory that uses none of them would struggle to show "appropriate" monitoring.

**Questions to keep.**
- "Does the Code require monitoring of chains of thought?" Not as a requirement: M3.5 example (11), for closed-weight models with hidden CoT.
- "What post-market monitoring methods does the Code list?" M3.5's eleven examples.
- "Must providers give external researchers access after release?" Yes: "will provide an adequate number of independent external evaluators with adequate free access to:" (continues).
- Should be asked but might not be: "How does the Code handle post-market monitoring of open-weight models?" Hardly at all, specifically: repositories in (7); (11) excludes them by design.

**Prediction for unit 33.** The access list: (1) the model's most capable version(s) (including with safeguards removed or "helpful-only" variants?), (2) chains-of-thought where available, (3) the model's API with adequate rate limits; "free" access; then conditions: providers may set confidentiality/security requirements; selection of evaluators via public criteria; perhaps an exception for SMEs, or "unless the model is open-weight, since access is already available". Possibly also a non-retaliation clause (no legal action against good-faith evaluators).
