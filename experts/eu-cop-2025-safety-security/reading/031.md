# Unit 31 · L251–265 · p.13: Measure 3.5, Post-market monitoring (first part)

**What it held.**
- "Signatories will conduct appropriate post-market monitoring to gather information relevant to assessing **whether the systemic risk could be determined to not be acceptable** (pursuant to Measure 4.1) and to inform whether a Model Report update is necessary (pursuant to Measure 7.6). Further, Signatories will use **best efforts** to conduct post-market monitoring to gather information relevant to producing **estimates of timelines** (pursuant to Measure 1.1, point (2)(c))."
- Post-market monitoring will: "(1) gather information about the model's capabilities, propensities, affordances, and/or effects; (2) take into account the exemplary methods listed below; and (3) **if Signatories themselves provide and/or deploy AI systems that integrate their own model, include monitoring the model as part of these AI systems**."
- Example methods (list continues): "(1) collecting end-user feedback; (2) providing (anonymous) reporting channels; (3) providing (serious) incident reporting forms;"

**What differed.**
- I predicted end-user feedback, anonymous channels, incident forms (yes, so far). Not predicted:
  - The purpose is framed **negatively**: information on whether the risk "could be determined to **not** be acceptable". Monitoring looks for evidence against acceptability. It's a disconfirmation search, not a confirmation exercise.
  - Monitoring also serves **timelines forecasting** (M1.1(2)(c)), with a softer standard: "best efforts". Real-world use reveals capabilities, and that informs when the next tier will be crossed.
  - Point (3): monitoring of the model **inside the signatory's own AI systems** (e.g. a chat product built on its own model). The model/system boundary of recital (b) is crossed again, for the provider's own systems.
- Same four objects as M3.2: capabilities, propensities, affordances, effects. The Code's evaluation ontology is consistent across pre- and post-market.

**Wandering.**

- **"Could be determined to not be acceptable."** That's an unusually careful framing. It says the purpose of monitoring is to find the evidence that would overturn acceptability. Good epistemics: monitoring as falsification. Paired with M1.2's escalation loop (monitoring is an input that can trigger a full reassessment), the post-market phase is designed to catch the case where the pre-market judgement was wrong.
- **"Best efforts" vs "will".** The Code differentiates its obligation strengths: "will" (firm), "best efforts" (softer, effortful), "as appropriate", "may". A fork extracting obligations needs to record the modal for each. For the lexicon of normative force, the Code has at least: commit to, will, will use best efforts, should (in recitals), may, recognise. That's a scale worth capturing when we translate assertions.
- **Own systems vs others' systems.** The signatory monitors its model inside its *own* AI systems. It doesn't say anything (yet) about monitoring the model inside third parties' systems (API customers, open-weight users). The provider's view into downstream deployments is limited to what it can see: API traffic, perhaps, and public reports. The open-weight case: once weights are out, post-market monitoring can be little more than feedback channels, incident forms and watching the internet. I expect a later example method about downstream or open-weight monitoring; if not, it's a gap.
- **Parentheticals again**: "(anonymous)", "(serious)". The Code uses parentheses to mark optional or qualified words: "(unredacted)", "(anonymous)", "(serious)". For "(serious) incident reporting forms", the forms serve for incidents, serious or not. For "(anonymous)", channels may be anonymous. This typographic habit carries meaning, and a fork should not drop parenthesised words when quoting.
- **Is end-user feedback a *systemic*-risk signal?** Mostly not at scale, but users are the first to notice capability surprises (e.g. a model doing something unexpected) and misuse. The Code's monitoring mixes individual-scale channels into systemic-risk work. Reasonable: systemic risks begin as individual incidents.

**Questions to keep.**
- "What is post-market monitoring for?" M3.5: information on whether the risk "could be determined to not be acceptable", whether a Model Report update is needed (M7.6), and (best efforts) timeline estimates.
- "Does the provider have to monitor its model inside its own products?" Yes, M3.5(3).
- "What about monitoring downstream third-party deployments, and open-weight models?" Not yet seen; watch the rest of the list.
- Should be asked but might not be: "How strong is each obligation?" The Code's modals vary ("will", "best efforts", "as appropriate"); record them.

**Prediction for unit 32.** The example list continues: (4) bug bounties; (5) collaborations with external researchers (research access, e.g. API credits); (6) monitoring of public sources (social media, forums, dark web?); (7) for open-weight models, monitoring of downstream fine-tunes/repositories; (8) usage-pattern analysis / privacy-preserving logging. Then maybe a paragraph on providing independent external evaluators with access post-market.
