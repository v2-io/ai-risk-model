# Unit 40 · L333–341 · p.16: Measure 4.2, Proceeding or not proceeding

**What it held.**
- "Signatories will **only proceed** with the development, the making available on the market, and/or the use of the model, **if** the systemic risks stemming from the model are determined to be acceptable (pursuant to Measure 4.1)."
- "If the systemic risks… are not determined to be acceptable **or are reasonably foreseeable to be soon not determined to be acceptable**…, Signatories will take appropriate measures to ensure the systemic risks… **are and will remain** acceptable prior to proceeding. In particular, Signatories will:
  - (1) not make the model available on the market, restrict the making available on the market (e.g. via adjusting licenses or usage restrictions), withdraw, or recall the model, as necessary;
  - (2) implement safety and/or security mitigations (pursuant to Commitments 5 and 6); and
  - (3) conduct another round of systemic risk identification…, analysis…, and acceptance determination…."

**What differed.** I predicted "only proceed if acceptable", and the market actions (not make available, restrict, withdraw, recall). Not predicted:
- **"Reasonably foreseeable to be soon not determined to be acceptable."** The trigger is anticipatory: you act before the risk becomes unacceptable if it's foreseeable that it soon will be. Precaution, recital (g), now applied to the go/no-go decision (not only to identification, as I wrongly concluded at unit 9).
- **"Are and will remain acceptable"**: the measures must secure acceptability going forward, not just now.
- **The "in particular" list is all about market availability**, mitigations and reassessment. It **doesn't name pausing development or stopping internal use**, though the governing sentence does ("only proceed with the development… and/or the use").

**Wandering.**

- **This is the Code's strongest sentence.** "Will only proceed with the development… if the systemic risks… are determined to be acceptable." A conditional prohibition on *development*. In plain terms: if a model under training reaches an unacceptable risk level, the signatory may not continue developing it until acceptability is restored. That's a pause commitment, written into an EU compliance instrument, voluntarily signed. A fork asked "does the Code require labs to pause?" should quote this sentence, and then add the next point.
- **The asymmetry between the rule and its "in particular" list.** The rule covers development, market and use. The listed actions (1) are market actions only. So what does "not proceeding with development" look like operationally? The Code doesn't say: no "pause training", "don't scale further", "don't deploy internally". The governing rule still binds (the list is "in particular", not exhaustive). But the operational content of a development pause is left to the signatory. This is exactly where my unit-12-to-20 internal-deployment pattern lands: the rule reaches development and use; the operational detail reaches only the market. A precise fork answer: "The Code says signatories will only proceed with development, market availability or use if risks are acceptable (M4.2). The specified measures for unacceptable risk are market restrictions, withdrawal or recall, mitigations, and reassessment; no measure specific to pausing development or internal use is listed."
- **Figure 3's missing exit**, revisited. The figure showed no "do not proceed" path. The text has one: (1)'s not making available / withdraw / recall. But it isn't an *exit*; it's a holding state while mitigations and reassessment happen: "take appropriate measures… prior to proceeding". So the figure is roughly right that the loop has only one exit (Acceptable → Proceed); not proceeding is the state of being in the loop. A model whose risk can never be made acceptable stays in the loop indefinitely, i.e. never proceeds. That's coherent. The Code has no notion of "abandon the model"; it just never gets to proceed.
- **"Withdraw, or recall the model"**: post-market action is envisaged. For an API model, withdrawal is feasible. For open weights, "recall" is impossible in practice; once released, it can't be withdrawn. So the Code's go/no-go for open-weight release has to be decided correctly before release; there's no post-hoc remedy. A fork should raise this when asked about open-weight models under the Code: the pre-release determination carries the full weight because (1) can't work afterwards.
- **"Adjusting licenses or usage restrictions"** as a form of restricting availability. So license terms are a risk control. Weak for open weights (license compliance is unenforceable at scale), stronger for API access.
- **"As necessary"** qualifies (1): not every unacceptability requires withdrawal; maybe mitigations suffice. (2) and (3) aren't qualified: mitigations and reassessment are always required when risk is (or soon will be) unacceptable.

**Questions to keep.**
- "Does the Code require providers to stop if risk is unacceptable?" M4.2: "will only proceed with the development, the making available on the market, and/or the use of the model, if the systemic risks… are determined to be acceptable."
- "What must a provider do if risk isn't acceptable?" M4.2(1)–(3): not make available / restrict / withdraw / recall "as necessary"; implement mitigations (C5, C6); reassess from identification.
- "Does the Code require acting before risk becomes unacceptable?" Yes: also if "reasonably foreseeable to be soon not determined to be acceptable".
- Should be asked but might not be: "What does a development pause look like under the Code?" Required by the rule, not operationalised in the list.
- Should be asked: "Can an open-weight release be recalled?" The Code lists recall; for open weights it's practically impossible, so the pre-release determination is decisive.

**Prediction for unit 41.** Commitment 5, Safety mitigations: Signatories commit to implementing appropriate safety mitigations along the entire model lifecycle, to ensure the systemic risks are acceptable. Measure 5.1 with examples: filtering training data, monitoring and filtering inputs/outputs, fine-tuning to refuse, staged access (API only, KYC), tools for downstream actors, techniques for safe ecosystem (e.g. agent IDs), alignment-oriented methods. Possibly a note on open-weight release considerations. LEGAL TEXT Art. 55(1)(b).
