# Unit 120 · L959–965 · p.42: Appendix 4.3, Hardening interface-access to unreleased model parameters (1)–(3)

**What it held.** "Signatories will harden interface-access to unreleased model parameters **while in use**…:
1. prevention of unnecessary interface-access…, through (a) **explicitly authorising only required software and persons** for access to model parameters, enforced through multi-factor authentication mechanisms, and **checked… at least every six months**;
2. reduction of the risk of vulnerability exploitation or data leakage, through (a) thorough review of any software interfaces with access to model parameters by a security team…, and/or automated security reviews… **at least to the same standard as the highest level** of automated security review used for other sensitive code;
3. reduction of the risk of model parameter exfiltration, through (a) hardening interfaces…, using methods such as **output rate limiting**; and" (continues)

**What differed.** Predicted: authorised access, reviewed code, extraction protection. Not predicted: the **six-monthly access review** and the "highest level of automated review used for other sensitive code" as a relative standard. Nothing about the model's own access to its weights (yet).

**Wandering.**
- **"Software and persons"**: access authorisation covers software, not only people. Relevant to AI agents running inside the lab: an agent is "software" needing explicit authorisation. Combined with 'insider threats' including AI models, this is a control against a model (acting through software) reaching its own weights.
- **Output rate limiting against exfiltration**: weights can be leaked through an interface slowly (steganographically, or via an API that returns parameter-derived data). Rate limiting bounds bandwidth. It also bounds distillation attacks? Not really (distillation uses normal outputs); this is about interfaces *with access to parameters*, i.e. internal tooling.
- **Relative standard** for code review: "at least the same standard as the highest level… used for other sensitive code". Self-referential to the firm's own practice: if it reviews payment code rigorously, weight-access code must be reviewed at least as rigorously. Clever: no external benchmark needed.

**Questions to keep.**
- "How must access to weights be controlled?" Appendix 4.3: only explicitly authorised software and persons (MFA, reviewed at least every six months); security review of interfaces with weight access (at least the firm's highest automated-review standard); interface hardening such as output rate limiting; (continues).
- Should be asked but might not be: "Does access control cover AI agents inside the lab?" "Only required software and persons" are to be authorised; an agent is software.

**Prediction for unit 121.** 4.3(4) monitoring/logging of interface access for anomalies; then 4.4 Insider threats: background checks for personnel with weight access; training on insider threats; (1) maybe "sandboxing" / limiting model access to its own weights and environment (the "without prejudice to Appendix 4.4, point (1)" that limited evaluator access, so 4.4(1) may be "limiting access to model weights" in a way that restricts evaluators' white-box access).

# Unit 121 · L966 · p.42: Appendix 4.3 (4)

**What it held.** "(4) reduction of the risk of insider threats or compromised accounts, through (a) **limiting the number of people who have non-hardened interface-access** to model parameters."

**What differed.** Need-to-know appears here, scoped to *non-hardened* access: the few people who can touch weights outside the hardened interfaces (researchers who need raw access). No anomaly-monitoring objective in 4.3.

**Wandering.** "Limiting the number": no number given. The core insider-risk control in practice: few people with raw weight access. "Insider threats or compromised accounts" pairs a hostile insider with an outsider using an insider's credentials. Insider-threat specifics are coming in 4.4.

**Questions to keep.** "How many people may have raw access to weights?" "Limiting the number of people who have non-hardened interface-access" (4.3(4)); no number.

**Prediction for unit 122.** Appendix 4.4 Insider threats: (1) "protection against… through (a) background checks/screening of personnel with access…"; (2) insider-threat awareness training; (3) "reduction of the risk of model self-exfiltration through (a) sandboxing the model, e.g. limiting the model's access to its own parameters or the network, monitoring its actions"; and the evaluator-access limit referenced in 3.5 may be (1).
