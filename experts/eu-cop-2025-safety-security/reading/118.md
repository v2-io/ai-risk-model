# Unit 118 · L945–952 · p.41: Appendix 4.2, Protection of unreleased model parameters (1)–(4)

**What it held.** "Signatories will protect **unreleased** model parameters by implementing security mitigations that achieve the following mitigation objectives:
1. **accountability over all copies** of stored model parameters across all devices and locations, through (a) a **secure internal registry of all devices and locations** where model parameters are stored;
2. prevention of unauthorised copying… to unmanaged devices, through (a) access management on all devices storing model parameters, with **alerts in case of copying to unmanaged devices**;
3. prevention of unauthorised access… during transport and at rest, through (a) ensuring model parameters are always encrypted…, including encryption with **at least 256-bit security** and with encryption keys stored securely on a **Trusted Platform Module (TPM)**;
4. prevention of unauthorised access… during temporary storage, through (a) ensuring model parameters are **only decrypted for legitimate use to non-persistent memory**;" (continues)

**What differed.** Predicted the themes (storage, access, transport). Not predicted: the **registry of all copies** (a weights inventory), and the technical specifics (256-bit, TPM, decryption only to non-persistent memory).

**Wandering.**
- **Weights inventory**: knowing where every copy lives is the precondition of protecting any. Labs train on clusters across clouds, with checkpoints everywhere; a registry is non-trivial. It also makes "securely deleted" (C6's end of duty) checkable.
- **"Unreleased"**: consistent with C6's end-of-duty rule (security until weights are public or deleted). Released (open) weights need no protection.
- **256-bit + TPM**: concrete crypto standards. RAND-style specifics. The "as appropriate" in (3)(a) softens "always encrypted" slightly; "including" makes 256-bit/TPM a minimum of the (a) measure.
- **Decrypted only to non-persistent memory**: weights never sit decrypted on disk. Strong, and relevant to insider threats including the model itself (a model with filesystem access can't find decrypted weights on disk). Though a model running in memory is, by necessity, decrypted in that memory: self-exfiltration from memory is the residual concern.

**Questions to keep.**
- "How must unreleased weights be protected?" Appendix 4.2: a secure registry of all copies; access management with alerts on copying to unmanaged devices; encryption in transport and at rest (at least 256-bit, keys on a TPM); decryption only to non-persistent memory for legitimate use; (continues).

**Prediction for unit 119.** 4.2 (5)–(6): restricting access to the minimum number of people (need-to-know), with logging/monitoring of access; secure deletion. Then 4.3 Hardening interface-access to unreleased models (APIs: rate limits, output filtering, inference-time protection against weight extraction via distillation?).

# Unit 119 · L956–957 · p.42: Appendix 4.2 (5)–(6), during use; physical access

**What it held.** "(5) prevention of unauthorised access to model parameters **during use**, through (a) implementing **confidential computing** as appropriate, using hardware-based, and attested **trusted execution environments**; and (6) prevention of unauthorised physical access to systems hosting model parameters, through (a) restricting physical access to data centres and other sensitive working environments to required personnel only, along with regular inspections of such sites for unauthorised personnel or devices."

**What differed.** My unit-118 note worried about weights decrypted in memory during use: (5) addresses exactly that with confidential computing / attested TEEs, "as appropriate". Physical security (6), predicted. No "need-to-know access" list here; that may be in 4.4 (insider threats).

**Wandering.**
- **Confidential computing for inference** (GPU TEEs, e.g. H100 confidential mode) was frontier practice in 2025; RAND's SL4-ish. "As appropriate" softens it: a firm might argue it's not appropriate below some tier. With M6.2's staging ("in line with the increase in model capabilities"), TEEs may be expected only for the most capable models.
- **The weight-security lifecycle is complete**: inventory → copying controls → encryption at rest/in transit → decryption only to memory → protection in use (TEE) → physical access. Six objectives. Combined with the Security Goal's quantified attacker (10 professionals, months, €1M) and insiders including models, it's a coherent, auditable regime.

**Questions to keep.** "Does the Code require confidential computing?" Appendix 4.2(5): "implementing confidential computing as appropriate, using hardware-based, and attested trusted execution environments".

**Prediction for unit 120.** Appendix 4.3 Hardening interface-access to unreleased model parameters: objectives such as limiting software interfaces that can access weights (only via approved, reviewed code); monitoring for unusual access patterns; protection against weight extraction through APIs; "secure the model's own access" (e.g. model can't access its weights during agentic tasks).
