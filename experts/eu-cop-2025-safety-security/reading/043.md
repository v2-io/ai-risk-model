# Unit 43 · L355–364 · p.17: M5.1 examples of safety mitigations

**What it held.** "Examples of safety mitigations are:
1. filtering and cleaning training data, e.g. data that might result in undesirable model propensities such as **unfaithful chain-of-thought traces**;
2. monitoring and filtering the model's inputs and/or outputs;
3. changing the model behaviour in the interests of safety, such as fine-tuning the model to refuse certain requests or **provide unhelpful responses**;
4. staging the access to the model, e.g. by limiting API access to vetted users, gradually expanding access based on post-market monitoring, and/or **not making the model parameters publicly available for download initially**;
5. offering tools for other actors to use to mitigate the systemic risks stemming from the model;
6. **techniques that provide high-assurance quantitative safety guarantees** concerning the model's behaviour;
7. techniques to enable safe ecosystems of AI agents, such as model identifications, specialised communication protocols, or incident monitoring tools; and/or
8. other emerging safety mitigations, such as for achieving transparency into chain-of-thought reasoning or **defending against a model's ability to subvert its other safety mitigations**."

**What differed.** I predicted seven of these categories closely (memory). Not predicted:
- **(6) high-assurance quantitative safety guarantees.** A research programme (guaranteed-safe AI) listed as a mitigation type.
- **(1)'s example**: data filtering aimed at *propensities*, specifically **unfaithful chain-of-thought**. Training-data hygiene for CoT faithfulness. I'd expected the CBRN example (remove dangerous knowledge).
- **(3)'s "provide unhelpful responses"**: not only refusal; deliberately degraded help.
- **(4)'s "initially"**: staged release can mean open weights *later*. The Code sees open-weight release as a possible last stage of staged access.

**Wandering.**

- **WG3's fingerprints.** Unit 1: Yoshua Bengio chairs WG3, which I assumed drafted the mitigation sections. Item (6) "high-assurance quantitative safety guarantees" is the vocabulary of the guaranteed-safe-AI agenda Bengio co-authored (with Dalrymple, Tegmark, Russell and others, 2024, as I recall), and of ARIA's Safeguarded AI programme. Item (8)'s "defending against a model's ability to subvert its other safety mitigations" is the vocabulary of AI control research (Redwood). Item (1)'s CoT faithfulness, and (8)'s CoT transparency, are 2025 alignment-research concerns. So the mitigations list is a snapshot of the 2024–25 frontier-safety research agenda, written in by research-oriented chairs. That's a lineage claim (author → text), plausible, not stated. A fork comparing the Code's mitigations with IASR's should know that the overlap may be authorial.
- **Loss of control is visible here without being named.** (1) unfaithful CoT, (8) CoT transparency and a model subverting its own mitigations: these address a model that might deceive or work against its overseers. The Chapter hasn't yet used the phrase "loss of control" in operative text, but the mitigations anticipate it. My priming: the loss-of-control formula ("reliably direct, modify, or shut down") is coming, probably in Appendix 1.4.
- **"Provide unhelpful responses"** is honest. Refusal is detectable (and invites jailbreaking); giving unhelpful answers is a quieter mitigation (sandbagging on purpose, for dangerous queries). It has transparency costs: users can't tell whether the model can't help or won't. Recital (f) wanted targeted methods that keep beneficial capability; unhelpful responses to *certain requests* is a targeted form.
- **Staged access as safety mitigation.** (4) makes release mode a mitigation. Combined with M3.5 (post-market monitoring informs expanding access) and M4.2 (restrict availability if needed), there's a coherent staged-release logic: start narrow (vetted users), monitor, widen; open weights only "initially" withheld, perhaps later released once the risk is shown acceptable. This positions open-weight release as *compatible* with the Code when it comes last and is justified.
- **(5) tools for other actors**: e.g. classifiers that downstream deployers can run, detection tools for AI-generated content, or vaccines-style countermeasures (bio-defence). The provider's mitigations reach beyond its own deployment.
- **(7) safe agent ecosystems**: "model identifications" (agent IDs), "specialised communication protocols", "incident monitoring tools". This is agentic-AI governance (2025 proposals on agent IDs and agent infrastructure). Again: the Code anticipates the model-in-system world while regulating models.
- **All are examples, "and/or".** No mitigation is required by name. The duty is appropriateness and robustness for acceptability.

**Questions to keep.**
- "What safety mitigations does the Code name?" M5.1's eight examples.
- "Does the Code address chain-of-thought faithfulness?" Yes: (1) filtering data that might cause "unfaithful chain-of-thought traces"; (8) "transparency into chain-of-thought reasoning".
- "Does the Code allow open-weight release?" It treats not releasing weights "initially" as a staged-access mitigation (M5.1(4)), implying later release may follow; the determination in C4 governs.
- Should be asked but might not be: "Does the Code anticipate AI control (models subverting safeguards)?" Yes, M5.1(8), and the safety margin's "subverted" (M4.1).
- "Whose research agendas shaped this list?" Possible authorial lineage (WG3 chair Bengio; guaranteed-safe AI; AI control). Inference.

**Prediction for unit 44.** Commitment 6, Security mitigations: Signatories commit to implementing an adequate level of cybersecurity protection for their models and physical infrastructure, along the lifecycle, to ensure risks from unauthorised release, access and/or model theft are acceptable. Measures 6.1 (security goal, maybe defined by threat actors: "non-state external threats, insider threats, other expected threat actors") and 6.2 (security mitigations, with Appendix 4 listing measures). Possibly exemptions for models "similarly safe or safer" (Appendix 2.2) or whose capabilities are already widely available.
