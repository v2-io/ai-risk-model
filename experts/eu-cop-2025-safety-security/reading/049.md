# Unit 49 · L410–411 · p.19: M7.1(4)(c)–(d), refusal topics and the system prompt

**What it held.** "(c) listing topics on which the model is intended to refuse instructions; and (d) providing the system prompt."

**What differed.** Both predicted in rough form ("categories of request", "the system prompt"). Brief, and specific: a **list of refusal topics** and **the system prompt** itself, not a description of it.

**Wandering.**
- **"The system prompt"**, singular and definite: as though a model has one. Real deployments have many (per product, per surface). And API models used by developers have the developer's system prompt, not the provider's. So "the system prompt" probably means the provider's own default/first-party system prompt(s). A fork should note the definite article as ambiguous for multi-surface deployments.
- **Refusal topics** listed: the AI Office learns what the model is meant to refuse. Combined with external evaluators' access to the helpful-only version (M3.5), the AI Office can compare intended refusals with the underlying capability. That's a well-designed pairing: capability without safeguards (from evaluators) vs intended safeguard behaviour (from the spec).
- **Confidential to the AI Office** (Art. 78): system prompts and refusal lists are commercially sensitive (and jailbreak-relevant). The Code collects them for the regulator only.
- M7.1 ends at (4)(d). The model spec, per the Code, has four parts: principles, prioritisation, refusal topics, system prompt. That's a compact, checkable definition of "model specification" for our lexicon, with the Code's "often known as" marking it as a borrowed industry term.

**Questions to keep.**
- "What must the Model Report say about the model's intended behaviour?" M7.1(4): principles; prioritisation among principles and instructions; topics it's intended to refuse; the system prompt.
- Should be asked but might not be: "Which system prompt, if there are many deployments?" The text says "the system prompt".

**Prediction for unit 50.** Measure 7.2, Reasons for proceeding: the Model Report states why the signatory determined the risks acceptable and decided to proceed: justification with reference to the acceptance criteria and safety margin; the uncertainties and assumptions; the role of mitigations; whether risk would remain acceptable under scenarios (e.g. weights leaked); and whether "similarly safe or safer" reasoning (Appendix 2) was used.
