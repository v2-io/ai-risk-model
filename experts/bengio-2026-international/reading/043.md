# 043 · L623–625 · p.21 · Table 1.2 stages 3–5 (**model vs system; deployment vs release**)

**Predicted:** post-training, system integration, deployment, monitoring. **Got:** 3, 4 and 5 (monitoring presumably next). This is one of the densest units for the lexicon so far.

**Stage 3, post-training and fine-tuning.** "'Post-training' further refines the base model to optimise it for **a specific application**". (Odd: for a *general-purpose* model, post-training mostly optimises for general assistant behaviour, not "a specific application". The definition fits fine-tuning for radiology better than RLHF for ChatGPT.) Defined terms: **'synthetic data'** ("artificially generated information that mimics real-world data but is created using algorithms or simulations"); **'supervised fine-tuning'**; **'reinforcement learning'** (rewarding and penalising, in quotes); **RLHF**; **'reinforcement learning with verifiable rewards' (RLVR)**, "for tasks that require factual correctness, such as maths or code generation". The last ties to the reasoning-model gains in maths and code (025). That's the mechanism behind the jagged frontier: domains with verifiable rewards advance fastest. The report doesn't draw this inference here; I do.
- "Developers typically alternate between applying post-training techniques and running tests until results show that the model meets **desired specifications**." Testing sits inside development, before deployment testing. Relevant to evaluation-awareness: models are trained *against* tests in a loop.

**Stage 4, system integration: the model/system distinction, made explicit with an example.** "GPT-5 … is a general-purpose AI **model** … while ChatGPT is a general-purpose AI **system** that combines several models … with a chat interface, content processing, Web access, and application integration". Clear and quotable. **The lexicon's `iasr:ai-system` = model(s) + components (interface, filters, tools, scaffolding) "ready for use"**. Components serve "capability, usefulness, and safety", e.g. a filter (citing Anthropic's Constitutional Classifiers, [industry]). **'scaffolding'**: "additional software built around general-purpose AI models that allows them to **plan ahead, pursue goals, and interact with the world**". So the *agentic* properties (planning, goals, acting) are located in the *scaffolding*, not the model. That's a notable ontological choice: agency as a system-level property conferred by scaffolding. (Compare 033: agents = "systems that can act in the world with limited human oversight".) Consistent: agents are systems.

**Stage 5, deployment and release.**
- "**Developers and deployers** implement AI systems into real-world applications". **"Deployer" appears as an actor distinct from "developer".** One company designs a customer-service bot "powered by another company's general-purpose AI system". That's the downstream deployer. For G2: IASR has at least *developer*, *deployer*, *data worker*, *compute provider*, *user* (and 042's "different developers" per stage).
- **Internal vs external deployment:** "internally (for their own use) or externally (for private customers or public use)". Internal deployment is named as a kind of deployment, which matters for LoC and risk management (frontier labs' internal use of models for R&D). Watch for it later.
- **"'AI system deployment'** refers to making a model available for real-world use with integrated tools and interfaces, while **'model release'** involves making the **base model** accessible to others – either as **open-weight** (downloadable parameters) or **closed-weight** (API access only)."
  - Two defined terms, deployment (system-level) and release (model-level). Good.
  - **But "base model" here conflicts with stage 2's definition** ("This process produces a 'base model'", the *pre-trained* model). Released models are almost always post-trained, not base models. So "base model" is used loosely here for "the model itself". A real terminological slip inside one table. **Should-ask: "In IASR, is an open-weight release a release of the base model?"** By stage 2's definition, no; by this sentence, literally yes. My reading: the sentence means "the underlying model", not the pre-trained base. Record it as an internal inconsistency.
  - **"closed-weight (API access only)"**: closed release = API access. But API access was also described as *deployment* (external access via APIs). So API access is both deployment and closed release. The deployment/release distinction is clean in the definitions and overlaps in practice. A fork mapping "release" to the EU's "placing on the market" or SB 53's "deploy" will need care.

Wandering:
- The model/system distinction will matter enormously for mapping obligations: SB 53 regulates "frontier models"; the EU regulates GPAI *models* (and AI systems separately); IASR describes both. When IASR says "systems" (most of its prose, e.g. "general-purpose AI systems are software programmes…"), it often means model+system loosely. The table is careful; the prose is not. Hypothesis: forks should treat table and definitional text as authoritative and prose as loose.

**Next, I predict:** stage 6: post-deployment monitoring and updates (usage monitoring, incident response, patches, retraining); then the text after the table on reasoning models.
